# Chat — rafael: explica o nó motor-memoria-vetorial

**Pergunta (rafael):** explica o nó motor-memoria-vetorial

**Resposta da Mind:** # Nó: Memória Vetorial (pgvector)

## O que é (segundo o registro)

É o **motor de busca semântica** da Mind, ativo, do domínio mind-plataforma. Funciona assim:

- A memória Markdown é quebrada em **chunks de 1000 tokens com overlap de 200** — padrão herdado do IGO AI Studio, que ficou como "banco de peças" (chunker, contrato de busca do `mcp-knowledge`, health-checks), nunca como dependência.
- Os embeddings são gerados pelo **Ollama local** (`nomic-embed-text`) — decisão explícita de Rafael (11/jun/2026) de não usar GPT/OpenAI.
- Os vetores ficam no **pgvector do mesmo Postgres do gateway** — sem Qdrant, sem serviço novo.
- Quem aciona é o **Orquestrador (core.ts)**, via busca híbrida.

## Duas regras importantes do registro

1. **Degradação graciosa**: a máquina do Ollama liga sob demanda; quando está desligada, a Mind **cai para busca lexical** — nunca trava.
2. **Regra inegociável de segurança**: `podeVer()` filtra **DEPOIS** da busca vetorial. Similaridade semântica não pode vazar documento confidencial.

## Riscos e lacunas que vejo NO REGISTRO

- **Filtro pós-busca**: o registro garante que nada vaza, mas filtrar depois significa que documentos confidenciais *participam* do ranking. Não há registro de como isso afeta a qualidade do resultado (ex.: top-K cheio de itens filtrados → resposta pobre para quem tem menos permissão).
- **Busca lexical como fallback**: não há registro de como/onde essa busca lexical é implementada, nem de qual a perda de qualidade esperada quando o Ollama está off.
- **Postgres compartilhado**: vetores no mesmo banco do gateway é decisão registrada, mas não há registro de plano para contenção de carga ou crescimento do índice.
- **Memória truncada**: o item 5 da decisão ("Orquestradores (de-para): o ...") está **cortado no registro**. Há um de-para de orquestradores cuja definição não consta aqui — lacuna real na memória ligada a este nó.
- **Sem registro de re-indexação**: nada sobre o que acontece quando um Markdown muda (re-chunk? re-embed? gatilho?).

## Para aprofundar o debate

1. Quando o `podeVer()` descarta muitos resultados do top-K, a busca deve **re-expandir** (buscar mais candidatos) ou aceitar resposta mais pobre — e isso deveria virar regra registrada no nó?
2. O item 5 da decisão de 11/jun está incompleto no registro — quer completar agora o de-para de orquestradores para fechar essa lacuna na memória?
